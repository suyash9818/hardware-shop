\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}

\begin{justifying}
Traditional e-commerce platforms are usually optimized for consumer products,
where catalog discovery depends largely on brand, price, popularity, and image
presentation. Hardware and industrial product domains operate under a different
set of requirements. Product identity often depends on engineering attributes
such as thread size, voltage, pitch, material grade, tolerance, connector type,
and dimensional constraints. Purchase decisions also depend on compatibility,
availability, procurement lead time, and inventory traceability. These needs
are not served well by rigid catalog schemas or purely descriptive product
pages. This project therefore investigates the design and implementation of an
Intelligent Hardware-Focused E-Commerce Platform using Django and Django REST
Framework.
\end{justifying}

\begin{justifying}
The final project extends an earlier catalog-and-inventory prototype into a
broader workflow-oriented system. The platform now supports modular
applications for catalog, cart, inventory, orders, pricing, manufacturing, and
returns management. Products are modeled with a combination of relational core
fields and a JSON-based specification structure that allows hardware-specific
attributes to vary by product type. The system includes product browsing,
search, product detail rendering, compatibility-oriented presentation,
session-based cart management, order creation, order submission, and a
rule-based fulfillment decision engine that selects inventory, supplier, or
manufacturing sources. Dashboards summarize operational state for inventory,
pricing, and manufacturing, a demo-ready quote flow estimates payment,
shipping, and tax behavior, and a browsable REST API exposes the system
programmatically.
\end{justifying}

\begin{justifying}
Validation depth also improved through framework checks, migration consistency
checks, route verification, and thirteen automated functional tests. These
tests cover specification-aware search, compatibility retrieval, cart quantity
accumulation, order totals, draft order creation, inventory-backed fulfillment,
supplier and manufacturing decision paths, serialized inventory handling, RMA
creation, quote-page rendering, and authenticated API access using JWT and DRF
token flows. The current system remains a prototype rather than a production
storefront, but it demonstrates a coherent end-to-end hardware-commerce
workflow with explicit limitations, measurable results, and a credible path for
future extension.
\end{justifying}

\noindent
Key Words: Hardware E-commerce; Django; Django REST Framework; Dynamic
Specifications; Compatibility; Inventory Tracking; Fulfillment Decision Engine;
Automated Testing.

\chapter{Introduction}

\section{Motivation}

\begin{justifying}
Hardware-focused digital commerce differs sharply from general online retail.
In a typical retail setting, the key user questions are often simple: what is
the item, how much does it cost, how is it rated, and how fast can it be
delivered. In a hardware environment, a much richer set of questions appears.
Will this connector fit the existing socket. Does this fastener match the
thread and pitch required by the assembly. Is the sensor compatible with the
operating voltage in the target system. Is stock available now, or must the
item be procured or manufactured. These questions reveal that a hardware
platform is not only a sales interface, but also a technical decision-support
environment.
\end{justifying}

\begin{justifying}
Many general-purpose e-commerce systems treat product attributes as either fixed
database columns or loosely formatted free text. Both approaches create
problems. A rigid schema becomes difficult to extend when new product families
introduce new attributes. Free text is easier to store but harder to query,
harder to validate, and harder to use for compatibility checks. This project is
motivated by the need for a middle-ground architecture that combines stable core
relational data with a flexible dynamic specification layer.
\end{justifying}

\section{Problem Statement}

\begin{justifying}
The problem addressed in this project is the design of a flexible and modular
hardware-commerce platform that can represent technical product specifications,
support compatibility-oriented browsing, maintain inventory visibility and
traceability, and provide the beginnings of realistic downstream fulfillment
logic. A working prototype must go beyond data storage. It must expose
catalogue views, search, shopping cart behavior, order creation, and a
transparent decision process that explains whether the system can fulfill an
order from existing stock or whether the request should move to supplier or
manufacturing workflows.
\end{justifying}

\section{Research and Design Questions}

\begin{itemize}[leftmargin=0.4in]
    \item How can hardware products be modeled without creating a new database schema for each product family.
    \item How can the system remain modular while still supporting end-to-end workflow behavior.
    \item What level of compatibility support is reasonable at a prototype stage without introducing excessive complexity.
    \item How can inventory, pricing, and manufacturing models be connected to order submission in a way that remains understandable and demonstrable.
    \item What evidence is needed to show that the prototype is not only structurally correct but also functionally meaningful.
\end{itemize}

\section{Objectives}

\begin{enumerate}[leftmargin=0.4in]
    \item Build a hardware-oriented catalog model with dynamic JSON-based specifications.
    \item Support product browsing, search, and compatibility-oriented presentation.
    \item Provide cart and order workflows that connect catalog selection to fulfillment logic.
    \item Maintain inventory visibility and optional serialized traceability.
    \item Model supplier and manufacturing planning data for downstream order decisions.
    \item Expose the system through a browsable REST API.
    \item Add automated tests to validate core end-to-end behaviors.
\end{enumerate}

\section{Final Project Contributions}

\begin{justifying}
Compared with the earlier seminar submission, the current version makes several
practical contributions. First, it introduces session-based cart behavior and
order submission, which transforms the project from a mostly informational
prototype into a transactional workflow. Second, it adds a rule-based
fulfillment engine that connects orders with inventory, supplier offers, and
manufacturing cost profiles. Third, it exposes system resources through Django
REST Framework, supplements them with a lightweight API documentation page, and
supports authenticated inspection through DRF token and JWT-based routes.
Fourth, it extends the operational scope with demo-ready payment, shipping, and
tax estimation plus a basic warranty/RMA workflow. Finally, it improves the
verification story through thirteen automated tests, which provide a stronger
quality-assurance layer than the earlier version.
\end{justifying}

\chapter{Related Work and Literature Review}

\section{Hardware Catalog Complexity}

\begin{justifying}
Hardware catalogs are naturally heterogeneous. A fastener uses attributes such
as thread, pitch, length, coating, and material grade. An electrical connector
uses pin count, voltage, current rating, ingress protection, and contact type.
A sensor uses measurement range, supply voltage, protocol, and mounting
details. A rigid relational schema that attempts to store all such fields at
once quickly becomes sparse and difficult to maintain. At the same time, a
fully unstructured text-only representation weakens search and validation. This
creates a natural need for hybrid modeling, which aligns with prior
configuration-oriented work in e-commerce decision support \cite{scholz-config}.
\end{justifying}

\begin{justifying}
The system developed in this project addresses this challenge by storing core
commercial fields such as SKU, name, category, and price in relational columns
while storing variable technical attributes inside a JSON field. This approach
does not solve every problem automatically, but it creates a practical
foundation. It allows categories to evolve, it reduces migration frequency for
minor attribute changes, and it makes it easier to experiment with different
hardware families during an academic prototype stage.
\end{justifying}

\section{Dynamic Specifications and Schema Flexibility}

\begin{justifying}
Flexible data representations are commonly used when product structures vary
significantly. In this project, flexibility is not pursued as an abstract
database ideal but as a direct response to hardware diversity. The dynamic
specification field allows a product page to render a technical table from
key-value pairs without requiring a special template or model for every product
type. In practice, this means that a bolt can expose \texttt{thread},
\texttt{pitch}, and \texttt{material}, while a sensor can expose
\texttt{voltage}, \texttt{range}, and \texttt{protocol}, all through the same
application structure.
\end{justifying}

\begin{justifying}
The tradeoff is that application logic must take responsibility for validation,
search behavior, and compatibility rules. This tradeoff is acceptable in a
prototype because it shifts complexity from schema maintenance to application
logic, where the developer can iterate more rapidly. It also aligns well with
Django's ability to render flexible content through templates and class-based or
function-based views, while retaining native support for JSON-backed model
fields in the framework stack \cite{django-docs}.
\end{justifying}

\section{Compatibility-Oriented Commerce}

\begin{justifying}
Compatibility is one of the defining properties of hardware commerce. A user
rarely purchases a technical part in isolation. Instead, the user wants to know
whether the selected item will function inside an assembly, fit an interface,
or satisfy a specification requirement. Full compatibility systems can become
extremely sophisticated. They may involve formal constraints, engineering
standards, graph relationships, or domain expert rules. Recommender-system
literature shows why more structured or knowledge-based approaches become
valuable when products have rich attributes and user decisions are constrained
by technical requirements \cite{scholz-config,zhang-ai-rec}.
\end{justifying}

\begin{justifying}
The present system does not attempt to implement a complete compatibility
engine. Instead, it introduces compatibility-oriented presentation through a modest,
interpretable heuristic. Products that share selected specification values, such
as \texttt{thread} or \texttt{voltage}, can be surfaced as potentially
compatible candidates in the product detail view. This provides educational
value and establishes a usable prototype foundation without overpromising full
engineering correctness. The dedicated \texttt{Compatibility} model also keeps
the design open for future explicit relations.
\end{justifying}

\section{Inventory Traceability and Serialized Units}

\begin{justifying}
Inventory control in hardware settings often extends beyond a simple numeric
quantity. Many commodity items can be managed effectively through count-based
tracking, but other items require individual traceability because of warranty,
quality assurance, regulatory compliance, maintenance records, or RMA handling.
For such cases, serialized unit tracking becomes important. The design in this
project therefore supports both aggregate stock and optional serial units. This
is consistent with broader manufacturing-traceability literature, which shows
that unit-level traceability and lifecycle visibility are important in quality,
complaint handling, and operational control \cite{traceability-review}.
\end{justifying}

\begin{justifying}
This hybrid strategy is useful from an educational perspective as well. It
demonstrates that inventory design is not a single-schema decision. Different
product types justify different traceability levels, and the platform must be
able to support both without forcing all items into a heavyweight serialization
workflow.
\end{justifying}

\section{Web Framework and API Support}

\begin{justifying}
Django is a strong fit for this project because it provides clear model-view
separation, a mature ORM, a built-in admin interface, URL routing, template
rendering, and testing tools \cite{django-docs}. Django REST Framework extends
these capabilities with serializers, viewsets, routers, permission classes, and
a browsable API \cite{drf-docs}. For a project that needs both human-facing
pages and machine-accessible endpoints, this combination is highly effective.
\end{justifying}

\begin{justifying}
The current project also uses Simple JWT endpoints and DRF token
authentication-related routes \cite{simplejwt-docs}. The API defaults to open
resource access for development convenience, but the report now documents a
working authenticated endpoint at \texttt{/api/auth/me/} that accepts either
JWT bearer tokens or DRF auth tokens. This reflects the project's current
prototype position more accurately than the earlier draft wording.
\end{justifying}

\section{Knowledge-Based Decision Support in E-Commerce}

\begin{justifying}
The present project is also connected to a broader literature on
knowledge-based and AI-assisted recommendation systems. Zhang, Lu, and Jin
survey the way recommender systems evolve from simple content matching toward
more knowledge-rich and explainable approaches when user needs become more
specific and item representations become more complex \cite{zhang-ai-rec}. This
observation is relevant to hardware commerce because the value of a suggested
item depends not only on similarity but also on whether technical requirements
can be satisfied.
\end{justifying}

\begin{justifying}
Scholz et al. argue that configuration-oriented recommendation is especially
useful when shoppers must reason about multiple constrained attributes rather
than make purely preference-driven selections \cite{scholz-config}. The current
seminar project does not implement a full product configurator, but it adopts
the same spirit by treating dynamic specifications, compatibility hints, and
fulfillment choices as interconnected decision-support artifacts. This makes
the prototype more appropriate for technical commerce than a generic retail
catalog would be.
\end{justifying}

\section{Positioning of the Present Work}

\begin{justifying}
A seminar report must position a prototype honestly with respect to prior work
and practical constraints. The present system therefore combines ideas from
knowledge-based recommendation, configurable e-commerce support, and
traceability-oriented inventory design without claiming to be a complete
industrial platform. Placeholder images from a lightweight image service are
used to keep the user interface coherent without requiring a large media
collection \cite{placeholdco}. This is not a production strategy, but it is an
effective prototype strategy for demonstrating architecture, workflow, and
evaluation evidence in a final academic submission. In that sense, the project
is best understood as a scoped synthesis of configurable recommendation and
traceability concepts rather than a fully optimized recommender platform
\cite{scholz-config,zhang-ai-rec,traceability-review}.
\end{justifying}

\chapter{Requirements, Scope, and Methodology}

\section{Development Methodology}

\begin{justifying}
The project follows an iterative prototype methodology. Instead of attempting to
design every subsystem in full detail before implementation, each development
iteration adds a bounded layer of capability and then stabilizes it through
debugging and verification. This approach is appropriate for a seminar project
because it supports continuous demonstration, clear before-and-after
comparisons, and incremental scope control. The move from a catalog-only
prototype to a workflow-oriented system in the final project reflects this
methodology.
\end{justifying}

\section{Functional Requirements}

\begin{enumerate}[leftmargin=0.4in]
    \item The system shall store hardware categories and products with dynamic specifications.
    \item The system shall provide list and detail views for products.
    \item The system shall provide a search route that can match text present in product identity and specifications.
    \item The system shall display compatibility-oriented suggestions on product detail pages.
    \item The system shall support session-based cart management.
    \item The system shall support draft order creation from the catalog.
    \item The system shall support order submission and order status transitions.
    \item The system shall select a fulfillment source based on inventory, supplier, or manufacturing data.
    \item The system shall track inventory and optionally support serialized units.
    \item The system shall expose data through REST API endpoints.
    \item The system shall include automated tests for major user and workflow paths.
\end{enumerate}

\section{Non-Functional Requirements}

\begin{itemize}[leftmargin=0.4in]
    \item \textbf{Modularity:} major business capabilities should be isolated into Django apps.
    \item \textbf{Extensibility:} new specification keys should not force schema redesign.
    \item \textbf{Transparency:} order decisions should be explainable through visible notes and statuses.
    \item \textbf{Usability:} the project should be demonstrable through human-readable pages and API screens.
    \item \textbf{Verifiability:} core behaviors should be testable through Django test cases.
    \item \textbf{Maintainability:} templates, views, and models should remain readable enough for future extension.
\end{itemize}

\section{Scope Boundaries}

\begin{justifying}
The final project intentionally does not attempt to solve all
enterprise-commerce problems. The current scope excludes production payment
processing, production-grade shipping integration, jurisdiction-specific tax
computation, customer-account checkout, strict permission design across all API
resources, and a fully operational reverse-logistics workflow. Although some of
these topics are represented through stubs or basic workflows, keeping them
within prototype scope keeps the implementation aligned with the academic
purpose of demonstrating architecture, data design, and core workflow
behavior.
\end{justifying}

\section{Prototype Assumptions}

\begin{itemize}[leftmargin=0.4in]
    \item The project uses SQLite as the development database.
    \item Product images are simulated through generated placeholders.
    \item Compatibility support is heuristic and illustrative rather than fully authoritative.
    \item The cart is session-based and does not require login.
    \item Most API endpoints remain open in development, while a small authenticated endpoint demonstrates token handling.
    \item Test data is created internally through Django tests rather than imported from a large benchmark dataset.
\end{itemize}

\section{Evidence Strategy}

\begin{justifying}
To satisfy final submission expectations, the project uses several forms of
evidence: working pages, screenshots, route verification, framework checks,
migration checks, and automated tests. This combination is important.
Screenshots help communicate the implemented workflow, but tests and route
checks provide stronger technical credibility. The report therefore includes
both narrative evidence and structured validation summaries.
\end{justifying}

\section{Evaluation Methodology}

\begin{justifying}
The evaluation approach for this project is intentionally mixed-method. It does
not rely on a single benchmark score because the prototype spans several
concerns at once: data modeling, user-facing workflow, API exposure, and
operational planning logic. The report therefore treats evidence as layered.
Framework checks and migrations evaluate structural correctness. Route
verification evaluates deployment completeness. Automated tests evaluate
functional correctness on controlled scenarios. Screenshots and dashboards
evaluate whether the implemented behavior is visible and interpretable to a
reviewer.
\end{justifying}

\begin{justifying}
This methodology is appropriate for a seminar project because it balances
engineering rigor with scope realism. A full industrial evaluation would
require larger datasets, realistic demand traces, user studies, security
audits, and performance testing under load. Those are beyond the current
project scope. However, the layered evidence strategy still provides enough
coverage to support reasoned conclusions about what the prototype already does
well and where it remains limited.
\end{justifying}

\chapter{System Architecture}

\section{High-Level Architecture}

\begin{justifying}
The system follows a modular Django architecture built around separate apps for
catalog, cart, inventory, orders, pricing, manufacturing, and RMA handling.
These apps are connected by shared product identifiers and by the
order-submission workflow. The project-level URL configuration exposes app
routes, token endpoints, the home page, and the REST API. SQLite is used as
the persistence layer during development, Django templates provide the
frontend, and Django REST Framework provides the API layer.
\end{justifying}

\section{Request Flow Overview}

\begin{justifying}
The user-facing request flow begins at the home page or catalog listing. A
user can search, open a product detail page, add an item to the cart, or create
a draft order directly from the product page. When the user submits the order,
the system computes a fulfillment decision and updates stock or planning records
accordingly. In parallel, management views and APIs expose internal state for
inspection. This architecture keeps the project easy to explain because each app
plays a visible role in the flow.
\end{justifying}

\section{Development Environment}

\begin{justifying}
The project uses Django with SQLite in a local development environment. This is
appropriate for rapid prototype iteration because it minimizes setup overhead
and simplifies migration management. The project also uses static templates,
CSS, and a small number of placeholder-media decisions that keep the interface
coherent without introducing deployment-specific storage concerns. While SQLite
is not intended as a final production database for a complex commerce platform,
it is suitable for current development and testing tasks \cite{sqlite-docs}.
\end{justifying}

\chapter{Data Model and Persistence Design}

\begin{justifying}
The catalog layer centers on the \texttt{Category} and \texttt{Product} models.
\texttt{Category} organizes products with a name and slug. \texttt{Product}
stores the key commercial and descriptive data needed by the rest of the
system. Each product has a SKU, name, category, price, optional description,
creation timestamp, and a JSON field named \texttt{specs}. This structure
allows a unified catalog implementation across multiple hardware families.

\section{Cart Models}

\begin{justifying}

\section{Inventory Models}

\begin{justifying}
The inventory app models two related but distinct ideas. \texttt{StockItem}
stores the aggregate quantity of a product at a warehouse and records whether
that item is serialized. \texttt{SerialUnit} then stores individual serial
numbers and state transitions for serialized products. This split is conceptually
useful because it avoids placing serialization overhead on all products while
still supporting traceability where required.
\end{justifying}

\section{Pricing and Procurement Models}

\begin{justifying}
Supplier-side planning is represented through four core models: supplier
records, supplier offers, cost-and-availability profiles, and procurement
orders. Supplier offers store purchase cost, minimum order quantity, available
quantity, and lead time. Cost profiles capture internal or contract
manufacturing cost and lead time plus reorder thresholds. Procurement orders
represent planned external replenishment actions created when a supplier path
is selected.
\end{justifying}

\section{Manufacturing Models}

\begin{justifying}
Manufacturing-side planning is represented through manufacturer records and
manufacturing-order records. A manufacturer record stores production partner
identity, while a manufacturing order records product, quantity, unit cost,
status, and expected delivery. This model is intentionally simple but remains
sufficiently expressive for seminar demonstration and evaluation.
\end{justifying}

\section{Warranty and RMA Models}

\begin{justifying}
The \texttt{RMA} model extends the project beyond initial order fulfillment and
into post-purchase support. Each record can reference a product, order, and
optionally a serialized unit, along with a reason, status, and timestamps. This
is intentionally a basic workflow rather than a full enterprise returns module,
but it is sufficient to demonstrate how traceability and customer-support
records can connect back to the same product and order data used elsewhere in
the platform.
\end{justifying}

\section{Persistence and Migration Strategy}

\begin{justifying}
The project relies on Django migrations for schema consistency. During this
finalization phase, additional migrations were added to align models with current
application behavior and to register newly activated modules such as the cart
application. Migration verification is especially important in a modular
project, because schema drift across apps can create import errors, route
failures, and confusing runtime behavior. The project therefore includes
explicit verification through \texttt{makemigrations --check --dry-run} and
\texttt{migrate --noinput}.
\end{justifying}

\subsection{Decision Logic}

\begin{justifying}
The decision engine follows a clear priority sequence. It first checks whether
inventory is sufficient. If so, inventory is chosen because it provides zero
lead time and no procurement or manufacturing delay. If inventory is not
sufficient, the system compares supplier offers and manufacturing cost profiles.
The current implementation sorts available candidates by cost and then by lead
time, ignores supplier offers whose available quantity is zero, and prevents
serialized stock from being used unless enough serial units are actually
available. If neither supplier data nor manufacturing profiles exist, the
system falls back to a placeholder manufacturing decision. This fallback is
honest about missing data while keeping the workflow operational.
\end{justifying}

\begin{algorithm}[H]
\caption{Simplified order fulfillment decision}
\begin{algorithmic}[1]
\ForAll{item in order}
    \If{available inventory quantity is at least requested quantity}
        \State choose inventory
    \Else
        \State collect supplier candidate if offer constraints are satisfied
        \State collect manufacturing candidate if cost profile exists
        \If{no candidates exist}
            \State choose manufacturing fallback
        \Else
            \State sort candidates by cost, then lead time
            \State choose best candidate
        \EndIf
    \EndIf
\EndFor
\State combine item-level decisions into an order-level explanation
\end{algorithmic}
\label{alg:fulfillment2}
\end{algorithm}

\section{Design Tradeoffs}

\begin{justifying}
Several design tradeoffs are visible throughout the implementation. JSON-based
specifications make the catalog flexible, but they move some validation burden
into application logic. Open-by-default API permissions make the prototype easy
to inspect, but they are not sufficient for production deployment. The
fulfillment engine is explainable and testable because it is rule-based, but it
is also heuristic and intentionally limited compared with full decision-support
software. These tradeoffs are acceptable in a seminar prototype because they
prioritize clarity, modularity, and demonstrability.
\end{justifying}

\section{Lessons Learned}

\begin{itemize}[leftmargin=0.4in]
    \item A modular Django architecture was sufficient to support catalog, operational, and API concerns without a large framework rewrite.
    \item Dynamic specifications were useful for hardware diversity, but they work best when paired with clear presentation logic and focused test coverage.
    \item Rule-based fulfillment created a strong middle ground between realism and explainability for an academic prototype.
    \item Automated tests had outsized value because they exposed errors that were not obvious from manual page inspection alone.
    \item Demo-ready payment, shipping, tax, and RMA flows made the system easier to discuss honestly as a prototype with visible extension points.
\end{itemize}

\section{Academic Contribution of the Prototype}

\begin{justifying}
The academic contribution of this work is not that it solves hardware commerce
in a fully general sense. Rather, it demonstrates a coherent reference design
for a technically oriented commerce platform in which flexible product data,
compatibility hints, inventory traceability, order-source decisions, and
service follow-up records can all coexist within one modular web application.
That reference design is useful because seminar projects are often evaluated on
whether they connect architecture, implementation, and evidence into a single
argument. The present system does that more effectively than a catalog-only
prototype would.
\end{justifying}

\begin{justifying}
The project also illustrates a practical lesson about scope management. A final
submission does not need every production concern to be solved in order to be
academically valuable. Instead, it benefits from making tradeoffs explicit,
implementing the most instructive workflows end to end, and verifying them
carefully. In this report, that means emphasizing explainable fulfillment,
dynamic specifications, operational dashboards, and targeted testing rather
than overclaiming industrial completeness.
\end{justifying}

\chapter{Limitations and Threats to Validity}

\section{Current Limitations}

\begin{justifying}
Despite the progress in the final project, the system remains a prototype. The
API is mostly open in development and should not be considered
production-ready from a security perspective. Compatibility reasoning remains
heuristic and depends on a small set of selected specification keys. The
placeholder image strategy is appropriate for demos but is not a substitute for
real catalog media. The cart is session-based and does not yet support
authenticated customer accounts or cross-device persistence. Payment, shipping,
tax, and RMA flows are intentionally partial and should be interpreted as
demonstration workflows rather than deployed services.
\end{justifying}

\section{Dataset and Evaluation Limits}

\begin{justifying}
The automated tests use internally created data rather than a large benchmark
catalog. This is appropriate for unit and functional tests, but it limits the
ability to claim broad empirical performance for search quality or compatibility
recommendation quality. A final report should therefore distinguish carefully
between correctness on controlled test cases and general performance on
real-world hardware datasets.
\end{justifying}

\section{Environmental Limits}

\begin{justifying}
The development environment uses SQLite and a local filesystem. This is a
reasonable choice for prototype development, but it can differ from production
behavior in concurrency, deployment structure, and media handling. The final
report therefore avoids presenting the current environment as a direct
production benchmark and treats it instead as a controlled academic
implementation context.
\end{justifying}

\section{Threats to Validity}

\begin{itemize}[leftmargin=0.4in]
    \item \textbf{Internal validity:} heuristic compatibility rules may overstate correctness if only small curated examples are shown.
    \item \textbf{External validity:} test cases based on small synthetic data may not generalize to larger industrial catalogs.
    \item \textbf{Construct validity:} visible workflow success does not guarantee a complete enterprise-commerce solution.
    \item \textbf{Presentation bias:} screenshots may emphasize polished paths while hiding under-tested edge cases.
\end{itemize}

\chapter{Future Work}

\section{Security Hardening}

\begin{justifying}
The highest-priority future improvement is API security. The project already
contains JWT and token-auth related routes, which means the next step is not to
invent a new auth strategy but to enforce appropriate permission classes on
resource endpoints. This will make the API more realistic and closer to a
production-capable service.
\end{justifying}

\section{Compatibility Reasoning Expansion}

\begin{justifying}
The current compatibility approach demonstrates feasibility, but the final
system should include richer logic. This could involve explicit compatibility
tables, category-specific rules, engineering constraints, or knowledge-graph
style relations. A stronger compatibility engine would also support a more
rigorous evaluation methodology in the final report.
\end{justifying}

\section{Search and Filtering}

\begin{justifying}
Search is currently based on text matching across key fields and serialized
specification content. A future version could introduce structured filters,
weighted ranking, synonym handling, or even a specialized search backend.
Because hardware discovery often depends on precise attribute combinations,
improvements in this area would substantially strengthen the practical value of
the project.
\end{justifying}

\section{Operational Integrations}

\begin{justifying}
Future operational integrations include payment processing, shipping,
tax-calculation services, and return management. From a system-design
perspective, the current modular structure is well positioned for these
extensions. Order workflows, dashboards, and API endpoints already provide the
organizational backbone required for such integrations.
\end{justifying}

\section{Expanded Testing}

\begin{justifying}
The existing thirteen tests should be treated as a strong starting point rather
than a complete verification story. Additional tests should cover API creation
and update operations, permission enforcement across more endpoints, supplier
and manufacturing record creation, serialization allocation details, invalid
order inputs, and more detailed dashboard assertions. Expanding test coverage
would not only improve robustness but also strengthen the academic quality of
the project by providing clearer evidence of engineering discipline.
\end{justifying}

\section{Formal Evaluation Study}

\begin{justifying}
The final report should include a broader evaluation chapter based on search
effectiveness, compatibility correctness, fulfillment decision correctness, and
system usability. If time permits, a small user study involving classmates or
reviewers could provide useful qualitative evidence regarding interface clarity
and perceived usefulness of compatibility suggestions and operational
dashboards.
\end{justifying}

\chapter{Conclusion}

\begin{justifying}
The final project marks a major step forward for the Intelligent
Hardware-Focused E-Commerce Platform. The system has evolved from a largely
structural prototype into a workflow-aware implementation that now includes
catalog search, compatibility-oriented product detail pages, a session-based
cart, order creation and submission, inventory-aware fulfillment logic,
supplier and manufacturing planning modules, dashboard views, a browsable API,
a demo-ready quote flow, a basic RMA module, and automated tests.
\end{justifying}

\begin{justifying}
Equally important, the system is now easier to communicate as an academic
project. The new modules provide visible evidence of progression from the
earlier submission, and the tests provide technical evidence that key behaviors
work as intended. Although the platform still requires security hardening,
richer evaluation, and broader integrations before it can be considered
complete, the present implementation provides a credible, well-scoped final
seminar project with clear future directions.
\end{justifying}
